# Кодекс денег — памятка

MVP, начат 12.09.2026 по мотивам обсуждения рынка LegalTech. Младший брат
«Кодекса детства» (`kodeksdetstva.ru`, репо `balibudda/kodeksdetstva`) —
та же архитектура (zero-dependency статический генератор, `node
scripts/build.mjs` -> `dist/`), но **не тот же код** — писался заново,
проще и меньше, специально под этот проект.

**Репозиторий публичный с 15.09.2026** (сделан открытым, чтобы Actions
были бесплатными — приватные репо на аккаунте `balibudda` упёрлись в
месячный лимит минут; полная история переписки/обсуждений при этом
сжата в один коммит и перезалита force-push'ем, публично не видна).
**Из-за этого — важное правило на будущее: ничего чувствительного
(реальные значения секретов, личные/деловые детали, пути к файлам с
ключами на компьютере Ника и т.п.) в этот CLAUDE.md/любой другой файл
репозитория не писать** — секреты только через `process.env`/GitHub
Secrets, обсуждение личного/делового — в чате, не в коммитах. `.jks`
keystore и его пароль как и раньше живут вне git, это не изменилось.

## Идея и позиционирование

Не «убить КонсультантПлюс/Гарант» (нереалистично — рынок LegalTech РФ
~20 млрд руб/год, туда уже вошли Яндекс Нейроюрист, Pravo.AI, ПравоТех).
Вместо этого — та же формула, что сработала у «Кодекса детства»: бесплатно,
понятным языком, ситуация → закон → шаги → контакты, **без рекламы платных
услуг**. Ниша выбрана намеренно: «финансы физлиц» (16% всех юридических
вопросов по исследованию СберПраво 2023-2024) — единственная категория,
где в топе поиска почти сплошь реклама платных юрфирм («банкротство под
ключ»), а не честный нейтральный разбор. У «прав потребителя» (12%) уже
есть official-портал «Защита прав 24/7» (Москва + Роспотребнадзор) — там
плотно, туда не пошли.

Баланс тьма/свет заложен **с первого дня**, не задним числом (это была
проблема, которую пришлось чинить постфактум в «Кодексе детства»): 3
раздела «беда» (приставы, коллекторы, банкротство) + 1 раздел «рост»
(личные финансы/накопления/инвестиции).

## Стек

Идентичный кодексу детства по духу: Node.js built-ins only, ни одной
npm-зависимости. Vercel (`buildCommand: node scripts/build.mjs`,
`outputDirectory: dist`). Домен `kodeksdeneg.ru` уже привязан к Vercel-
проекту `bali-budda-s-projects/kodeksdeneg`, но **DNS ещё не настроен** —
нужно добавить у регистратора `A kodeksdeneg.ru -> 76.76.21.21` (или
переключить неймсерверы на Vercel — см. `vercel domains inspect
kodeksdeneg.ru`). До этого сайт доступен только по прямой ссылке
`*.vercel.app`, но она за SSO-стеной Vercel (`ssoProtection:
all_except_custom_domains` — снимается автоматически для подтверждённого
кастомного домена, трогать не нужно).

## Реальный трафик идёт не на Vercel, а через Cloudflare → GitHub Pages зеркало (13.09.2026)

Тот же паттерн, что и у kodeksdetstva/childofgod: DNS `kodeksdeneg.ru`
переключён на Cloudflare (обход блокировки Vercel IP в РФ), который
проксирует на GitHub Pages отдельного публичного репозитория
`balibudda/kodeksdeneg-web` — **не на Vercel напрямую**. Vercel по-прежнему
собирается на каждый пуш и был бы актуален, но реальные посетители видят
именно зеркало.

Зеркало было опубликовано один раз (162 темы) и не обновлялось — Ник
заметил («тем не стало 170»). Исправлено: `.github/workflows/
sync-pages-mirror.yml` в этом репозитории при каждом пуше в `main` сам
собирает `dist/` и пушит его в `kodeksdeneg-web` (сохраняя `CNAME`, которого
`build.mjs` сам не генерирует). Токен для кросс-репо пуша — секрет
`MIRROR_PUSH_TOKEN`. **Если сайт выглядит «не обновился» — сначала
проверять зеркало, не Vercel** (`curl -sI https://kodeksdeneg.ru/` →
`x-github-request-id`/`via: 1.1 varnish` подтверждают GitHub Pages).

## Новости почти никогда не добавлялись — две реальные причины (14.09.2026)

Ник заметил: «почему никаких новостей не добавляется». Бот исправно
запускался каждый день (`schedule` в `daily-news-check.yml`), но за
месяц с лишним реально добавил **одну** новость. Обе причины нашлись
через прямую проверку истории прогонов (`gh run list`/`gh run view --log`),
не гадание:

1. **Окно поиска «за последние 1–2 дня» в `news-check-prompt.md` было
   нереалистично узким** в сочетании со строгими требованиями к
   источнику (только официальные ведомства/крупные СМИ с точной
   ссылкой) — событие, подходящее под оба критерия одновременно, редко
   случается ровно в день прогона. Расширено до 7 дней; требования к
   источнику/уникальности текста не трогал — осознанная политика Ника.
2. **`--max-turns 40` в самом workflow оказался слишком тесным** —
   когда бот РЕАЛЬНО находит и пишет полноценную новость (веб-поиск +
   проверка источника + пересказ на 1000+ символов + сборка + коммит),
   это легко занимает 45+ шагов. `claude-code-action` в этом случае
   засчитывает превышение лимита как ОШИБКУ ВСЕГО ПРОГОНА, даже если
   сам агент по факту успешно дописал работу (`"is_error": false` в
   логе, видно через `gh run view --log`) — и откатывает результат:
   никакого коммита не остаётся, будто работа не делалась вовсе. Поднят
   до 70; повторный прогон с этим фиксом запущен для проверки — если
   снова упрётся в лимит на бОльшем числе шагов, поднимать дальше.

**Если бот снова «молчит» подолгу** — не считать это по умолчанию

(значит пользователь ею управляет), сама публикация может упасть с
`"Application does not have permission for this action"` (code 10,
subcode 2069007) или `"нет разрешения на загрузку видео"` (code 6000,
subcode 1363042) — **входит ли страница в список `me/accounts` и есть ли
у ПРИЛОЖЕНИЯ реальный грант на публикацию туда — два разных вопроса.**

`pages_manage_posts`-токена это разрешение реально применилось к этой
конкретной странице (Facebook в новом флоу отдельно спрашивает, к каким
страницам разрешить доступ — если страница появилась ПОСЛЕ того, как
токен был выдан для другой, старой страницы, новую нужно доразрешить).
**Фикс: заново пройти Generate Access Token в Graph API Explorer** — на
этот раз получить токен **уже сразу как Page Access Token** (не User
Token) — проверяется через `GET /v21.0/me?fields=id,name` с этим
токеном: если возвращает саму страницу (не пользователя) — это Page
Token, и с ним публикация уже проходит. Тестировать перед сохранением в
секреты: пробный `POST /{page-id}/feed` с текстом → если прошёл, сразу
удалить тестовый пост (`DELETE /{post-id}`) и сохранить токен.

**YouTube — та же путаница с каналом, что и у kodeksdetstva, только хуже**:
этот же Google-аккаунт (владеет и kodeksdetstva, и kodeksdeneg как
Brand Account) при ЛЮБОЙ попытке OAuth (тот же клиент, новый клиент,
новый Cloud-проект, свежее инкогнито-окно, явное переключение активного
канала в Studio перед авторизацией) стабильно резолвил `mine=true` в
**kodeksdetstva**, никогда в kodeksdeneg — 5+ попыток подряд, включая
полностью новый, никогда не использовавшийся OAuth-клиент
(`kodeksdeneg-social`). Похоже, у Google-аккаунта есть «свой»
дефолтный/основной канал (видимо, kodeksdetstva), и простая
`mine=true`-авторизация всегда резолвится в него, независимо от того,
что выбрано активным в интерфейсе. **Единственное, что сработало**:
добавить `&authuser=1` (или другой индекс) прямо в саму ссылку
авторизации — заставляет Google отдать другой профиль/контекст. Если
`authuser=1` не сработает в следующий раз — пробовать `authuser=2` и
т.д., либо как самый надёжный вариант — завести отдельный Google-аккаунт
специально под конкретный канал и передать ему владение (Studio →
Настройки → Разрешения), чтобы канал стал «свой» для этого аккаунта, а
не управляемый Brand Account.

**НИКОГДА не отзывать доступ приложению целиком** через
myaccount.google.com/permissions в попытке «сбросить и начать заново» —
это revoke'ает разом ВСЕ каналы/токены, выданные этому OAuth-клиенту,
включая уже рабочие (чуть не снесли доступ к kodeksdetstva, пытаясь
починить kodeksdeneg — вовремя остановились).

## Android-приложение (Capacitor) — та же технология, что у kodeksdetstva (14.09.2026)

По прямой просьбе Ника («Сделать apk такой же как на кодекс детства с той же
технологией и ссылку в подвал поставить») — `npx cap add android` создал
`android/` (обёртка `dist/` в нативный WebView через Capacitor), appId
`ru.kodeksdeneg.app`. Toolchain (JDK 21, Android SDK headless) — тот же, что
уже настроен на машине Ника для kodeksdetstva, см. его CLAUDE.md за полным
описанием установки `sdkmanager`/`temurin`; здесь только то, что отличается.

**Иконка/сплэш** — не тот же самописный PNG-кодек, что у kodeksdetstva:
`scripts/gen-app-icons.mjs` рендерит через уже имеющийся в devDependencies
Playwright тот же брендовый глиф, что и в `public/favicon.svg` (знак ₽ в
кольце, цвет `#3a4f6b`/кремовый), сразу в 1024/2732px — четыре файла в
`resources/` (`icon.png`, `icon-foreground.png`, `icon-background.png`,
`splash.png`). Дальше как обычно: `npx capacitor-assets generate --android
--assetPath resources --iconBackgroundColor '#3a4f6b' ...` — **обязательно
`--assetPath resources`**, иначе инструмент найдёт папку `assets/` (это
папка сайта — `nav.js`/`search.js`/`styles.css`, не иконки) и молча
остановится на ней, не дойдя до `resources/`.

**capacitor.config.json — `html5mode: false`** (взято прямо из рабочего
конфига kodeksdetstva, не «по умолчанию»): без этого — тот же баг с
extensionless-путями (`/раздел/тема/`), который там ловили дважды за одну
сессию (`net::ERR_CONNECTION_REFUSED`, локальный сервер Capacitor умеет
гарантированно отдавать только `/` или путь с расширением файла).
**Фикс навигации перенесён сразу, не дожидаясь бага** — в `assets/nav.js`:
внутри приложения (`window.Capacitor.isNativePlatform()`) все клики по
внутренним ссылкам дозаписывают `/index.html` на конец.

**Подпись релиза** — своя, отдельная пара ключей, НЕ общая с kodeksdetstva
(намеренно, тот же принцип «не смешивать» — как с YouTube/Google Cloud
проектами). `android/keystore.properties` (в `.gitignore`) + `.jks`-файл
и пароль — оба вне git полностью (Ник знает, где они лежат).
**Та же критичность, что и у kodeksdetstva: потеря `.jks` = невозможность
когда-либо обновить приложение под тем же appId** — бэкапить отдельно от
git. `android/app/build.gradle` читает `keystore.properties` и подписывает
`release`-сборку, если файл существует (иначе собирается неподписанным —
`apksigner verify` в этом случае покажет `Verified: false`).

**14.09.2026 — путь с кириллицей ломал сборку, пока не пофиксили сам
Gradle-код.** Сборка v1.1.0 упала с «Keystore file not found» — Ник сам
переместил `.jks`-файлы и файлы с паролями в новую папку с кириллицей
в пути, чтобы на рабочем столе не было лишнего. Настоящая
причина ошибки — не сам перенос, а то, что `build.gradle` читал
`keystore.properties` через `keystoreProperties.load(new
FileInputStream(...))`: у `Properties.load(InputStream)` дефолтная
кодировка ISO-8859-1, а не UTF-8, поэтому кириллица в значении
`storeFile` превращалась в мусор (`ÐÐ¸ÐºÐ¾Ð»Ð°...`), и путь не находился,
хотя сам файл был на месте. **Исправлено на уровне кода, не обходом**:
`build.gradle` теперь читает файл явно как UTF-8
(`keystorePropertiesFile.withReader('UTF-8') { reader ->
keystoreProperties.load(reader) }`) — тот же фикс применён и в
kodeksdetstva. После этого путь с кириллицей работает штатно,
`./gradlew --rerun-tasks assembleRelease` проходит и подпись верна
(`apksigner verify` → v2 scheme true) — можно спокойно держать keystore
в этой папке и дальше, никакой отдельной ASCII-папки не нужно.
Serial number keystore’а kodeksdeneg — `f062023e29ea8413` (сверить через
`keytool -list -v`, если когда-нибудь будут сомнения, тот ли это файл).

**Бейдж версии и проверка обновлений** — тот же паттерн, `@capacitor/app` →
`App.getInfo()` + сверка с `/app-version.json`. **Одно отличие от
kodeksdetstva, сделанное намеренно**: запрос идёт на **абсолютный** URL
(`https://kodeksdeneg.ru/app-version.json`), а не относительный путь.
Причина: `app-version.json` — обычный файл в `public/`, копируется в
`dist/` при каждой сборке сайта и точно так же попадает внутрь самого APK
(Capacitor копирует весь `dist/` в ассеты приложения) — относительный
`fetch('/app-version.json')` внутри WebView с `html5mode: false` рискует
уйти на локальный (замороженный на дату сборки APK) файл вместо реального
файла на живом сайте, что сделало бы проверку обновлений бессмысленной
(сравнение версии самой с собой). Абсолютный URL гарантированно уходит в
сеть. Стоит перепроверить при случае, не унаследован ли этот же нюанс у
kodeksdetstva.

**Публикация APK**: тот же паттерн — приватный репозиторий не отдаёт
Release-ассеты анонимным посетителям, поэтому отдельный **публичный**
репозиторий `balibudda/kodeksdeneg-releases` (только APK, без исходного
кода). Кнопка «📱 Скачать APK для Android» в подвале сайта ссылается на
`.../releases/latest/download/kodeksdeneg.apk` — имя ассета всегда
одинаковое при новом релизе, тогда ссылка не меняется.

Сборка + релиз вручную:
```
node scripts/build.mjs && npx cap sync android
cd android && JAVA_HOME=/opt/homebrew/opt/openjdk@21 ANDROID_HOME=/opt/homebrew/share/android-commandlinetools ./gradlew assembleRelease
gh release create vX.Y.Z app/build/outputs/apk/release/app-release.apk \
  --repo balibudda/kodeksdeneg-releases --title "..." --notes "..."
  # переименовать ассет в kodeksdeneg.apk при загрузке, если gh не подхватил имя сам
```
Перед каждым релизом поднять `versionCode`/`versionName` в
`android/app/build.gradle` **и** синхронно обновить `public/app-version.json`
— иначе бейдж «Доступно обновление» просто не появится у тех, кто уже
установил приложение, без всякой ошибки сборки.

Первый релиз (v1.0.0, `versionCode` 1) собран и опубликован 14.09.2026,
подпись проверена через `apksigner verify --verbose` (v2 scheme: true).
RuStore — подача вручную Ником, не автоматизируется отсюда (см.
CLAUDE.md kodeksdetstva про требования: физлицо без ИП, targetSdk ≥ 28,
RSA ≥ 2048 бит — здесь всё то же самое выполняется).

## Гоча поиска: неоднозначное слово в синонимах перетягивает результаты (14.09.2026)

Ник прислал скриншот — запрос «криптовалюта развод» (это один из чипов
быстрого поиска) выдавал темы про раздел имущества при разводе, а тема
про крипто-мошенничество не попадала даже в топ-10. Две реальные
причины, обе исправлены в `assets/search.js`/содержимом темы, не в
алгоритме скоринга:

1. **Словарь синонимов `SYN` резолвит неоднозначное слово только в
   одну сторону.** `'развод'` вёл только к `'раздел имуществ'`
   (расторжение брака), хотя на этом сайте у слова есть и второй смысл —
   разговорное «развели на деньги» (тема `mnogostupenchataya-shema-
   razvoda` его как раз использует). Добавлено `'обман'` в то же
   направление — но НЕ весь блок `'мошенничеств'` целиком: проверено на
   симуляции скоринга (см. ниже), что это перекашивает голый запрос
   «развод» в сторону мошенничества, хотя он чаще всего именно про
   брак. `'развели'`/`'разводят'` (однозначные глагольные формы,
   почти всегда про обман) — получили полное направление.
2. **Заголовок темы не содержал буквально главное слово запроса** —
   `kriptovalyuta-moshennichestvo-shemy` называлась «Криптомошенничество:
   ...», без слова «криптовалюта» — формула скоринга даёт ×10 за точное
   совпадение в заголовке, и без него тема проигрывала любому топику,
   где искомое слово встретилось в заголовке буквально. Переименовано
   в «Мошенничество с криптовалютой: ...». **Урок на будущее**: у новой
   темы заголовок должен буквально содержать самое очевидное
   существительное, по которому её будут искать, а не только
   стилистически более яркую формулировку (в `keywords`/`seoDescription`
   этого недостаточно — там вес ниже).

**Как проверять поиск, не гадая**: скопировать функции `norm`/`stem`/
`tokens`/`expand`/`fieldHit`/`score`/`prep` из `assets/search.js` в
отдельный Node-скрипт (они не трогают DOM, кроме самого `input`/`out` в
IIFE) и прогнать по `dist/search-index.json` — так был реально
установлен и перепроверен весь разбор выше, а не догадка по одному
скриншоту. Пробовал более глубокий пересмотр самой формулы скоринга
(учёт покрытия разных слов запроса — сколько РАЗНЫХ терминов нашло хоть
что-то, а не просто сумма весов по полям) — он чинил один попутно
найденный мелкий эффект (генерик-мошеннические темы перетягивают
широкие запросы вроде «обманули с билетами»), но ценой отката фикса по
самому «криптовалюта развод». Решил не внедрять — слишком хрупкий
компромисс менять формулу скоринга для всего сайта (192 темы, десятки
реалистичных запросов, руками не перепроверить) ради частичного эффекта,
когда точечный фикс данных уже решил заявленную проблему с явным
запасом.

**Второй заход в тот же день** — Ник прислал ещё скриншот: «мошенники
звонят» показывал легальные темы про коллекторов (`Коллекторы звонят
вашим родственникам`/`...и угрожают`) выше настоящих тем про
мошеннические звонки. Тот же класс бага, третий раз подряд:

3. `SYN['звонят']`/`['звонит']` безусловно подтягивали `'коллектор'` —
   разумный выбор для голого «звонят» (коллекторские темы и без этой
   инъекции ранжируются первыми — совпадение по самому слову «звонят»
   в их заголовках, проверено), но при сочетании с «мошенники»
   перебивало реальные темы про мошеннические звонки термином,
   которого в запросе вообще не было. Убрана инъекция `'коллектор'` из
   этих двух ключей — осталось только `'звон'` (и `'мошенник'` у
   `'звонит'`, было и раньше).
4. Тема `kriptovalyuta-moshennichestvo-shemy` после фикса заголовка
   (пункт 2 выше) стала настолько плотной по словам «мошенничество»/
   «обман» (и в заголовке, и в keywords), что начала перетягивать
   НЕСВЯЗАННЫЕ запросы вроде «обманули с билетами» и «мошенники в
   Telegram» — детально повторяемый паттерн: топик, где основной
   generic-корень раздела (`мошенничество`/`обман`) продублирован и в
   заголовке, и в keywords одновременно, получает несоразмерный буст
   почти на любой запрос того же раздела, даже когда он специфически
   не о нём. Убрано дублирование слова «обман» из title/seoDescription/
   keywords этой темы (только «Мошенничество» + «криптовалюта»
   остались — по ним и так находится).
5. Из-за пункта 4 придуманный мной чип «криптовалюта развод»
   (искусственная фраза, два голых слова через запятую — так реальные
   люди не формулируют запрос) перестал побеждать в топе — вместо
   дальнейшей подгонки контента под одну искусственную фразу заменил
   сам текст чипа на «мошенники с криптовалютой» (естественнее и
   отлично работает без компромиссов с другими запросами) в обоих
   местах, где стоит `quickSearchBox()`.

**Общий вывод по обоим заходам**: при добавлении новой темы в раздел
`moshennichestvo` — не дублировать родовое слово раздела
(«мошенничество»/«обман»/«развод») одновременно и в заголовке, и в
keywords без надобности: это не помогает найти именно эту тему (она и
так в разделе про мошенничество), зато даёт ей неоправданное
преимущество перед специфичными темами на любой обобщённый запрос.
Заголовок и keywords должны содержать то, что уникально ИМЕННО для
этой схемы (конкретный способ: SIM, QR-код, Telegram, билеты,
криптовалюта, благотворительность...), родовые слова раздела и так
подтягиваются через `_s` (поле раздела) и общие синонимы.

set`, живо протестированы (тестовый `POST /feed` → сразу `DELETE`) на
обеих страницах. **Если токен снова «умрёт» быстро — не гадать, сразу
`debug_token`, почти наверняка тот же корень: забыли шаг Extend.**

## TikTok — общий аккаунт на оба проекта @kodeksrazuma (15.09.2026)

По прямой просьбе Ника — не заводить отдельный TikTok-аккаунт на каждый
сайт («чтобы сильно не заморачиваться»), один общий канал **«Кодекс
Разума»** (`tiktok.com/@kodeksrazuma`) на оба проекта: вечерний
комедийный ролик каждого сайта публикуется туда же, вперемешку с чужим.
Имя предложил сам Ник — нейтральное, не привязано ни к деньгам, ни к
детям конкретно.

**Приложение переиспользовано у nikolablajen-app** — то же самое TikTok
Developer-приложение (`TIKTOK_CLIENT_KEY`/`_SECRET`), что уже работает
для аккаунтов Николы (`@nikola.blajen`/`@nikola.blajen7`) — новое
приложение и повторное ревью TikTok не нужны, один Developer app может
авторизовать сколько угодно аккаунтов. Ключи скопированы одноразовым
workflow в `nikolablajen_app` (создан, запущен через `gh workflow run`,
удалён сразу после — тот же паттерн, что уже применялся для миграции
секретов `nikolablajen-media`).

**Публикация — черновик, не автопост.** Приложение всё ещё в статусе
Sandbox (заявка на scope `video.publish`, нужный для полной публикации,
была отклонена TikTok 14.09.2026) — используется только `video.upload`:
ролик уходит во входящие TikTok, Ник сам нажимает «Опубликовать» в
приложении. `@kodeksrazuma` добавлен в Sandbox → Target Users в
Developer Portal (обязательный шаг для Sandbox — без него авторизация
падает с `non_sandbox_target`).

**Реальная, неочевидная причина финального сбоя авторизации (стоило
больше часа разбора)**: TikTok валидирует `redirect_uri` интерактивного
`/v2/auth/authorize/` **по Production-конфигу приложения, а не по
Sandbox**, даже когда авторизующийся аккаунт — Sandbox target user.
Redirect URI в Sandbox-вкладке портала визуально сохраняется и
переживает перезагрузку страницы, но на реальную проверку при
авторизации не влияет вообще. У nikolablajen-app в Production
зарегистрирован **старый домен** `nikolablajen.com/tiktok-auth` — его
никогда не обновляли после переезда сайта на `.ru` (12.09.2026), а
Production-правки у TikTok требуют повторного ревью (не быстрая
правка поля). Подтверждено эмпирически: прямой запрос к authorize-URL с
`redirect_uri=…ru/tiktok-auth` — стабильно падал с `error_type=
redirect_uri`; тот же запрос с `.com` — сразу показал экран согласия.
**Фикс — не бороться с Production-ревью, а просто использовать
работающий `.com`**: он 301-редиректит на `.ru` (см. nikolablajen-app
CLAUDE.md, «Domains»), так что код авторизации всё равно приходит на
живой `.ru`-сайт с полным query string. Поправлено в самих скриптах
`nikolablajen-app/scripts/social/{tiktok-authorize,tiktok-post}.mjs`
(константа `REDIRECT_URI`) — держать эти два файла синхронными, если
понадобится подключать ещё один аккаунт этим же способом.

**Общий аккаунт → общий refresh_token, синхронизация между репо.**
TikTok ротирует `refresh_token` при каждом использовании — старый после
этого не работает. Поскольку `@kodeksrazuma` публикует из ДВУХ
независимых репозиториев (kodeksdeneg и kodeksdetstva), а не из одного,
`scripts/social/post-tiktok.mjs` (идентичная копия в обоих проектах)
после каждого обновления токена пишет новый `TIKTOK_REFRESH_TOKEN`
**сразу в оба репозитория** (`REPOS` константа в файле) — иначе тот
проект, что публикует вторым, получил бы уже протухший токен из своей
локальной копии секрета. `GH_TOKEN` для этой самозаписи — переиспользован
уже существующий `GH_ASSETS_TOKEN` (классический PAT с scope `repo`, тот
же, что используется для временного хостинга видео под Facebook).

**Технически**: `scripts/social/post-tiktok.mjs` — загружает готовый
ролик в TikTok inbox как черновик (`POST /post/publish/inbox/video/
init/` → `PUT` байтов), печатает текст описания в лог workflow-рана
(у draft-эндпоинта вообще нет поля подписи — Ник копирует текст вручную
при публикации). Подключён в `daily-comedy-post.mjs` третьим каналом,
рядом с YouTube/Facebook, в общем `try/catch` (сбой TikTok не блокирует
остальные каналы). Секреты в обоих репозиториях идентичны:
`TIKTOK_CLIENT_KEY`/`_SECRET`/`_REFRESH_TOKEN`.

**Пилот (первые 2 ролика)** — уже опубликованные на YouTube/Facebook
дипфейк-голос (деньги) и финансовые ловушки (детство) добавлены в
TikTok черновиками вручную в тот же день (локальные файлы уже не
сохранились — временно захостил на GitHub Release, скачал в
одноразовом CI-workflow, опубликовал, удалил за собой релиз и workflow).
Дальше — автоматически, каждый вечер, из обычного пайплайна.

## Два реальных бага — вечерний ролик 15.09.2026 не вышел вообще (16.09.2026)

Ник заметил: «вчера не вышли вечером мультяшные ролики». Нашлись ДВЕ
независимые причины, обе исправлены и проверены живым прогоном:

1. **`claude-code-action` ломает git-аутентификацию для следующего шага.**
   Сам экшен перенастраивает git credentials под себя (свой временный
   токен для своих операций — видно в логе: «Configuring git
   authentication… Removing existing git authentication headers… Updating
   remote URL with authentication token») и оставляет репозиторий в
   состоянии, непригодном для обычного `git push` следующим шагом —
   падает с `remote: Invalid username or token. Password authentication
   is not supported`. Из-за этого весь `write-script` job 15.09.2026
   упал целиком. **Фикс**: перед `git commit`/`push` в шаге «Закоммитить
   сгенерированный сценарий» явно восстанавливаем аутентификацию —
   `git remote set-url origin "https://x-access-token:${GH_TOKEN}@github.com/${{ github.repository }}.git"`
   (`GH_TOKEN: ${{ github.token }}`).
2. **`post`-джоб checkout'ил СТАРЫЙ коммит, не видел свежий сценарий.**
   `actions/checkout@v4` без явного `ref` берёт `github.sha` — коммит,
   которым СТАРТОВАЛ весь workflow, а не текущий HEAD ветки. `write-script`
   пушит `comedy-script.json` уже ПОСЛЕ старта workflow — `post`-джоб этот
   коммит не видел вообще, тихо падал на `comedy-script.json не найден —
   использую пилотный сценарий`, а поскольку пилот уже был опубликован
   раньше — просто ничего не делал. **Job показывал `success`, но по факту
   ничего не публиковал** — тот самый обманчивый паттерн «зелёная галочка
   не значит, что реальная работа была сделана», который уже ловили на
   `daily-news-check.yml` (см. выше). **Фикс**: `actions/checkout@v4` в
   `post`-джобе теперь с явным `ref: main`.

Оба бага, скорее всего, существовали с самого начала (14.09.2026), просто
не проявлялись — первый прогон брал `PILOT` по умолчанию (пустая
очередь), и код НИКОГДА реально не доходил до ветки «сценарий сгенерирован
и его нужно закоммитить/увидеть» до этого дня. **Проверено живым
прогоном 16.09.2026 после фикса**: оба джоба прошли, `write-script`
сгенерировал новую тему (`lzheprisatv-po-telefonu`), `post` её реально
увидел, отрендерил и опубликовал (YouTube + TikTok прошли; Facebook —
отдельная, третья проблема, см. ниже).

**Тот же класс бага стоит проверить в `daily-social-post.yml`** (утренний
формат) при случае — там нет двух джобов с зависимостью, поэтому первый
баг (аутентификация) там не применим, но чек-лист «job success ≠ реальная
публикация» стоит держать в голове для любого будущего двухджобного
workflow.
